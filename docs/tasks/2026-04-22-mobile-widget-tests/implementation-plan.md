## Risks surfaced during planning

- **Risk:** `MainScreen.dispose()` calls `getIt.resetLazySingleton<...>()` for several services. If the test's `tearDown` order causes the widget to dispose *after* `GetIt.I.reset()` (e.g., if `pumpWidget` state is unwound between tests in an unexpected order), those `resetLazySingleton` calls hit an empty container and throw.
  **Why it matters:** the second and third tests would fail with a `get_it` assertion rather than the assertion being tested, masking the real signal.
  **Mitigation:** rely on `flutter_test`'s automatic widget-tree teardown (which fires before the test's explicit `tearDown`). If a test fails this way, switch to calling `await tester.pumpWidget(Container())` at the end of each test body to dispose `MainScreen` before `GetIt.I.reset()` runs. Note in the standards doc.

- **Risk:** `AuthService` may call additional `AuthRepository` methods beyond `watchAuthState()` and `getIdToken()` during construction or initial frames (e.g., `getCurrentUser()`).
  **Why it matters:** an unstubbed mocktail call returns `null` for nullable returns but throws `MissingStubError` for non-nullables — surfacing as a flaky first test.
  **Mitigation:** while authoring step 6, run the empty-state test once and read the failure. Add stubs for any method `AuthService` actually invokes (`getCurrentUser()` → `async => null`, `signOut()` → `async {}`, etc.). Don't pre-stub speculatively.

- **Risk:** Services on the recipes tab pull from sibling repositories during `didChangeDependencies` — `RecipesCollectionListService.loadRecipesCollections()`, `ShoppingListListService.loadShoppingLists()`, `MealPlanListService.loadMealPlans()`, `MealPlanCalendarService.goToWeek()`. Each calls a repository method that must be stubbed, or the test fails on `MissingStubError` even when the assertion is purely about `RecipeGrid`.
  **Why it matters:** the test file's stub block grows beyond just `recipeRepository`. Underestimating this in step 6 turns it from a single-test increment into a debugging session.
  **Mitigation:** in step 6, after writing the empty-state assertion, run the test and add minimal stubs (`thenAnswer((_) async => [])` or equivalent) for each `MissingStubError` until it goes green. Keep the stubs at the top of `setUp` to make the cross-feature surface visible.

- **Risk:** `MealPlanVisibilityService` constructor reads from `PreferencesService` synchronously, which in turn uses `SharedPreferences`. The design covers this with `SharedPreferences.setMockInitialValues({})`, but it must also have a `PreferencesService` registered in `getIt` *before* `setupMealPlan` runs. The test `setUp` outline in `design.md` § Interface contracts does not show `PreferencesService` registration explicitly.
  **Why it matters:** missing this registration causes a `getIt` lookup failure inside `MealPlanVisibilityService`'s constructor on first lazy access.
  **Mitigation:** in step 6 `setUp`, after `SharedPreferences.setMockInitialValues({})` and `GetIt.I.reset()`, register a real `PreferencesService` (via `await SharedPreferences.getInstance()` and `getIt.registerSingleton(PreferencesService(prefs))`) before any `setup*()` call — mirroring the order in `lib/main.dart`. Document this in the standards file.
